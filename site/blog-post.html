RELEASE · OCTOBER 2, 2026

Cloud OS v0.4.0: remote access gets simpler

Cloud OS v0.4.0 focuses on making day-to-day server ownership more predictable. The update flow now exposes clearer stages, verifies the installed package after an update, and keeps rollback behavior explicit when installation fails.

Remote access also gets a simpler dashboard workflow. An Owner or Admin can connect an existing remotely-managed Cloudflare Tunnel using its tunnel token. Cloud OS stores that token server-side and never returns the raw secret through the status API or dashboard after configuration.

The integration page now reports connector state, the detected cloudflared version and a redacted startup diagnostic when the connector cannot remain running. This makes errors such as a disconnected tunnel easier to investigate without placing credentials in screenshots or support messages.

Cloud OS does not automatically create Cloudflare DNS or Published Application routes. The public hostname still needs to point at the correct tunnel configuration, and Internet-facing deployments should use additional access controls such as MFA.

SECURITY · SEPTEMBER 29, 2026

Why Cloud OS keeps privileged operations explicit

A browser terminal can be one of the most powerful parts of a server dashboard, so Cloud OS treats it as a high-trust capability rather than a convenience feature.

Role-based access control separates Owner, Admin, Operator, Member and Viewer permissions. Terminal execution is available only to roles that have the terminal permission. Audit events record terminal activity without storing the raw command text in the audit entry.

Cloud OS also avoids silently bypassing operating-system privilege controls. On Windows, a browser request cannot bypass UAC to turn an unelevated Cloud OS process into an Administrator shell. On Linux, privileged requests rely on the host's configured sudo behavior.

Authentication uses persistent progressive cooldowns after repeated failures. The goal is to keep privilege escalation visible and controlled instead of hiding security-sensitive behavior behind the dashboard.

RECOVERY · SEPTEMBER 26, 2026

Verified backups: recovery before convenience

A backup is useful only when it can be trusted during recovery. Cloud OS full backups therefore include a manifest containing SHA-256 integrity information, file sizes and package metadata.

Before a restore begins, Cloud OS verifies the selected backup. A failed integrity check stops the restore rather than copying untrusted or damaged data into the live server state.

For additional recovery safety, the restore workflow creates a pre-restore backup of the current state before replacing files. If restoration fails partway through, Cloud OS performs a best-effort rollback.

These backups are application recovery packages, not bare-metal operating-system images. They currently remain local and unencrypted, so operators should protect the backup directory and use an additional secure off-device backup strategy for important deployments.

ARCHITECTURE · SEPTEMBER 22, 2026

A cloud layer, not another operating system

Cloud OS is intentionally not a replacement operating system. Windows or Linux continues to boot and own the hardware; Cloud OS runs above it as a management layer.

That architecture lets an existing computer become a personal server without requiring a custom kernel or a destructive OS installation. The dashboard brings system health, restricted file management, users, teams, backups, integrations and host terminal access into one browser interface.

Host-native behavior remains explicit. Windows terminal sessions use PowerShell and Linux sessions use Bash. File operations are constrained to the configured Cloud OS storage root, while terminal commands execute with the permissions of the Cloud OS host process.

This approach keeps Cloud OS lightweight enough for repurposed personal hardware while preserving the underlying operating system and its normal administration model.
